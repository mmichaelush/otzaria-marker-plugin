# ארכיטקטורת תוסף המרקר

מסמך תחזוקה. מי שרוצה להבין מה התוסף עושה — [מדריך המשתמש](USER_GUIDE.md);
מי שרוצה לדעת על איזו גרסת אוצריא הוא נשען — [COMPATIBILITY](COMPATIBILITY.md).

## תמונה כללית

התוסף בנוי סביב הפרדה אחת מרכזית: **מה שנרשם באוצריא בלי שום קוד JS** מופרד
ממה שדורש מנוע חי.

```
manifest.json          תרומות דקלרטיביות: תפריט הקשר, פקד סרגל, קיצורי מקשים
  │                    אוצריא קוראת אותן ב-Dart בעליית התוכנה, בלי מנוע JS
  ▼
index.html       ──►  domain → i18n → en.js → runtime → core → ui
```

| קובץ | אחריות | מה אסור בו |
|------|---------|-------------|
| `js/marker-domain.js` | כללי דומיין טהורים: נרמול, טווחים, בניית payloads, סינון ומיון | DOM, SDK, timers |
| `js/marker-i18n.js` | קטלוג תרגום, בחירת שפה, תרגום ה-DOM | לוגיקה עסקית |
| `js/marker-runtime.js` | הגבול היחיד מול ה-SDK: `call`, שגיאות, לוגר, תור, הגנת אירועים | DOM, כללי דומיין |
| `js/marker-richtext.js` | עורך ההערות וה-sanitizer שמפעיל את מדיניות הדומיין | SDK, כללי דומיין |
| `js/marker-core.js` | המנוע: הגדרות, מאגר ההדגשות, התרומות, החלת/הסרת סימון, גיבוי, דיווח | DOM |
| `js/marker-ui.js` | הדף בלבד: rendering, טפסים, דיאלוגים | קריאת SDK ישירה, כללי דומיין |
| `i18n/en.js` | קטלוג אנגלית. המפתחות הם מחרוזות המקור בעברית | — |

הגבולות האלה אינם המלצה: `test/compatibility.test.js` נכשל אם `marker-domain.js`
נוגע ב-DOM, אם מודול כלשהו קורא ל-`Otzaria.call` ישירות, או אם `marker-core.js`
מזכיר את ה-DOM.

## מודל המופע היחיד

**לתוסף אין מופע רקע, וזו החלטה ולא השמטה.**

אוצריא מחזיקה בעלות על הדגשות **לפי מופע**: `PluginBridgeAdapter.dispose`
קורא ל-`PluginHighlightRegistry.removeInstance`, וכל סימון שאותו מופע צייר
נמחק איתו. מופע רקע הוא ארעי מטבעו — הוא נסגר כמה דקות אחרי שהוא מתבטל — ולכן
כל סימון שהוא היה מצייר בעליית התוכנה היה נעלם מעצמו זמן קצר אחר כך. ניסיון
להחזיק אותו בחיים (`keepAlive`) לא פותר: הדף אינו יכול למחוק או לעדכן רשומה
שהוא אינו בעליה, ואין ערוץ בין מופע למופע — כך שמחיקת סימון הייתה נשברת לצמיתות.

לכן: **דף התוסף הוא המופע היחיד שמצייר.** `MarkerDomain.ownsEngine` מחזיר
`false` רק עבור `runMode: 'background'`, כרשת ביטחון אם מופע כזה ייווצר אי
פעם. אין `app.run_on_startup`, אין `activationEvents`, אין `background.html`.

מה שנשאר עובד בלי מנוע חי הוא בדיוק מה שדקלרטיבי במניפסט: תפריט ההקשר, פקד
הסרגל וקיצורי המקשים. לחיצה על אחד מהם מעירה את הדף, והלחיצה נמסרת לו אחרי
ה-boot.

**עדכון תפריט ההקשר מותר מכל מופע.** פריטי התפריט רשומים ברמת התוסף (מהמניפסט),
ולכן `reader.updateContextMenuItem` מעדכן את אותה רשומה ומה שמעודכן שורד את
סגירת הדף. **רישום** פריט חדש (`add`) הוא מסלול נפילה בלבד — רישום נקשר למופע
הרושם, ואוצריא מנתבת לחיצות למופע קדמי גלוי שרשם את הפריט.

## תפריט ההקשר — למה הוא דקלרטיבי

`contributes.startup.contextMenuItems` במניפסט רושם שני פריטים עוד לפני שקיים
מנוע JS:

| id | סוג | הקשר | תפקיד |
|----|-----|------|--------|
| `marker-colors` | `color-row` או `submenu` | `reader-selection`, `reader-page-shape-selection` | בחירת צבע לסימון |
| `marker-highlight-actions` | `submenu` | `reader-highlight` | פעולות על הדגשה קיימת |

הפריט השני הוא תת-תפריט ולא שני פריטים, מפני שהמכסה היא שני פריטים עליונים
לתוסף ושורת הצבעים תופסת אחד. ילדיו:

| id | פעולה | הערה |
|----|--------|-------|
| `marker-note` | ערוך הערה | `openPlugin: true` — רק הדף יכול להציג עורך |
| `marker-remove` | הסר סימון | פועל headless, בלי לפתוח את הדף |

### לחיצות אינן מותנות בבעלות על המנוע

**זו הייתה תקלה אמיתית, ושווה לזכור אותה.** אוצריא מוסרת אירוע *ממוקד* —
לחיצה על פריט תפריט, על פקד סרגל, או קיצור מקלדת — למופע **אחד בלבד**
(`dispatchEventToPlugin` בוחר controller יחיד). לעומת זאת אירוע *שידור*
(`reader.sectionContentChanged`, `settings.changed`) מגיע לכל המופעים החיים
(`dispatchEvent`, לולאה על `targetControllers`).

מכאן:

- **מטפלי לחיצה אינם בודקים `isEngine`.** אין כפילות למנוע. הבדיקה גרמה לכך
  שאוצריא ניתבה לחיצה למופע שה-`isEngine` שלו `false` — והלחיצה נעלמה בלי
  שגיאה בשום מקום. לחיצה על צבע פשוט לא עשתה כלום.
- **מטפלי שידור כן בודקים `isEngine`**, אחרת אותה עבודה תרוץ פעמיים.

לחיצה עשויה להיות מה שהעיר את המופע, ואז היא נמסרת מיד אחרי שיגור
`plugin.boot` — בזמן שה-handler שלנו עדיין קורא מהאחסון. לכן כל מטפל לחיצה
ממתין ל-`whenBooted()` לפני שהוא נוגע ב-`settings`.

זה מה שמאפשר לתפריט לעבוד מהשנייה הראשונה של אוצריא, בלי שהתוסף עלה. הצבעים
במניפסט הם ברירות המחדל; כשהמנוע מתעורר (`app.startup`) הוא **מעדכן** את הפריט
לצבעים ולשפה של המשתמש דרך `reader.updateContextMenuItem`. `reader.addContextMenuItem`
הוא מסלול נפילה בלבד — למקרה שההרשאה `app.startup_contributions` בוטלה.

### המחק בשורת הצבעים

הסרת סימון זמינה בשני מקומות, ולא במקרה. `marker-remove` יושב בהקשר
`reader-highlight`, וה-host בונה את ההקשר הזה רק כשהלחיצה הימנית נופלת בדיוק
על סימון **וגם אין בחירה פעילה** (`_buildClickedHighlightEntries`). מיד אחרי
סימון בדרך כלל *יש* בחירה, ולכן התפריט הולך למסלול `reader-selection` —
שבו, עד גרסה 0.9.5, לא היה שום מחק. הפעולה הייתה קיימת ובלתי נגישה.

לכן שורת הצבעים נגמרת בערך `mark-clear`: `color: '#00000000'` (שקוף מלא, כך
שה-host מצייר את האייקון במקום גוש צבע) עם `icon: 'eraser_24_regular'`. זו
בדיוק התבנית שהמרקר של אוצריא עצמה משתמשת בה. לחיצה עליו מסירה כל סימון
שנוגע בבחירה — חפיפה ולא הכלה, כי מי שגורר בערך מעל סימון מצפה שהוא ילך.

`toSafeHex` נעקף עבור הערך הזה בכוונה: הוא שומר שש ספרות hex והיה הופך את
השקוף לשחור אטום.

### שתי מגבלות של המארח בשורת הצבעים

1. **הכותרת אינה מוצגת, בשום רוחב.** `AppContextMenuEntry.colorRow` במארח
   מקבל רשימת צבעים בלבד וקובע `label = null` בבנאי; ה-`title` שהתוסף שולח
   נזרק. זו אינה בעיית מקום. מי שרוצה לראות „מרקר” בתפריט בוחר בסגנון
   תת-תפריט, שכן מציג שם ואייקון. אין לפצל את הכותרת לפריט עליון נפרד —
   המכסה היא שני פריטים, והשני תפוס בפעולות על הדגשה.
2. **`selected` מצויר כטבעת עבה בצבע ה-primary** (3px), ולא כסימון עדין.
   סימון צבע ברירת המחדל בדרך הזו נראה כתקלת רינדור, ולכן התוסף אינו שולח
   את השדה.

`MarkerDomain.menuSignature` חוסם עדכון מיותר: הפונקציה מקודדת רק את מה שהתפריט
באמת מציג (סגנון, צבעים פעילים, שמות, שפה), כך ששינוי גודל גופן אינו גורם
לקריאת RPC.

### מה נעלם ביחס לגרסה הקודמת

בגרסה 0.9.x התוסף עקב אחרי `reader.selection_changed`, שמר את הבחירה האחרונה,
פענח בעצמו בחירה רב-שורתית עם `reader.findTextOccurrences`, והוסיף/הסיר את פריט
"הסר סימון" מתוך שורת הצבעים בכל שינוי בחירה. כל זה נמחק:

- **`selection.sections`** (0.9.97) — אוצריא מעגנת בעצמה כל פסקה בבחירה
  רב-פסקתית ומוסרת אותה ב-payload של הלחיצה. אין יותר ניחוש עוגנים.
- **הקשר `reader-highlight`** (0.9.97) — "הסר סימון" הוא פריט נפרד שאוצריא מציגה
  רק כשלוחצים על הדגשה בפועל, עם `selection.clickedHighlights`. אין יותר בדיקת
  חפיפה בכל שינוי בחירה, ואין מוטציה של התפריט תוך כדי גלילה.
- כתוצאה מכך ההרשאות `events.subscribe:reader.selection_changed`,
  `events.subscribe:navigation.changed` ו-`events.subscribe:reader.current_ref_changed`
  אינן נדרשות יותר, וכל מכונת המצבים של `savedSelection` / `selectionRevision`
  / `queueMenuTask` ירדה.

## מחזור החיים של ההדגשות

הדגשות חיות בשני מקומות: `storage` של התוסף (מתמיד) והזיכרון של אוצריא (נמחק
בכל הפעלה מחדש). `reconcileHighlights()` הוא הפעולה שמיישרת ביניהם, וזו אותה
פעולה גם בעלייה קרה וגם בהתעוררות חמה:

1. קריאה אחת ל-`reader.getHighlights({ includeStale: true })`.
2. רשומה שאינה אצל ה-Host — מצוירת מחדש (`reader.setHighlight`).
3. רשומה שקיימת אך `version` / `etag` / `status` / `range` שלה זזו — נשמרת מחדש.

בעלייה קרה זה אומר ציור של הכול; בהתעוררות חמה זו קריאה אחת בלי אף כתיבה.

`normalizeHighlight` הוא השער היחיד לרשומה: הוא מוחק שדות לא מוכרים, פוסל רשומה
בלי עוגן שמיש, ומחזיר תמיד את אותו מבנה. רשומה פגומה מדולגת ולא מפילה את הטעינה.

### חוזה ה-payload של ה-Host

`reader.setHighlight` אינו סובלני: הוא דוחה שדה לא מוכר, ערך מחוץ לרשימה
סגורה, וטווח מספרי חורג. הנקודה שהכי קל להיכשל בה היא `metadata.source` —
ה-Host מקבל **רק** `manual`, `ai`, `import` או `sync`. ערך אחר מוחזר כ-
`error.invalid_params: unsupported highlight source`, ואף הדגשה אינה נוצרת.
לכן כל ה-metadata נבנה בנקודה אחת, `MarkerDomain.buildHighlightMetadata`,
שגם חותכת את התגיות לפי מגבלות ה-Host (עד 20, עד 64 תווים, בלי ריקות).

**ה-harness אוכף את החוזה הזה.** `test/helpers/harness.js` מחקה את
`PluginHighlightRegistry` ואת `ContextMenuRegistry`: allowlist של שדות, ערכים
סגורים, טווחים, ופרסינג מחדש של פריט תפריט **אחרי המיזוג** של ה-patch. זו לא
קפדנות לשמה — גרסה קודמת שלחה `source: 'marker'`, כל הדגשה נכשלה באפליקציה,
וכל הבדיקות עברו בירוק מפני שה-fake קיבל כל דבר.

### חוזה הרשומה

```
highlightId  groupId  bookId  bookUid  book  sectionIndex
colorId  color  style  text  ref  note  tags  favorite
sourceRange  version  etag  status  timestamp
```

- מפתח האחסון הוא `highlight:<highlightId>` — `isSafeHighlightId` מוודא שהמזהה
  אינו יכול לצאת מהמרחב.
- `groupId` משותף לכל חלקי בחירה רב-פסקתית. חלקים כאלה תמיד נמחקים יחד
  (`expandByGroup`).
- `bookUid` הוא המזהה היציב שאוצריא ממליצה לשמור. `book` נשמר לצדו כ-fallback
  חינני, כפי שהתיעוד דורש.

## מחזור החיים של הדף

הדף עולה כשהמשתמש פותח את לשונית התוסף, וגם כשאוצריא מעירה אותו בעקבות לחיצה
על פריט תפריט או על פקד הסרגל. בכל עלייה הוא טוען את ההדגשות מהאחסון ומצייר
אותן מחדש (`reconcileHighlights`) — האחסון הוא המצב הסמכותי, לא מה שמצויר.

`reader.sectionContentChanged` נשמר כמנוי כדי שדף פתוח יגיב מיד לשינוי נוסח.
כשהדף סגור אין מה לעדכן בזיכרון, וה-Host מעגן מחדש את ההדגשות בעצמו; ה-reconcile
בעלייה הבאה קורא ממילא את המצב הסמכותי.

לחיצה עשויה להיות מה שהעיר את הדף, ולכן היא נמסרת מיד אחרי `plugin.boot` — בזמן
שהאחסון עדיין נקרא. כל מטפל לחיצה ממתין ל-`whenBooted()` לפני שהוא נוגע
ב-`settings`.

## הערות עשירות — ואיפה גבול האבטחה

הערה נשמרת פעמיים: `noteHtml` הוא ה-markup שמוצג, ו-`note` הוא מראה הטקסט שלו.
הטקסט הוא מה שמזין את החיפוש, את ייצוא ה-Markdown והטקסט, ואת הנפילה עבור
רשומות שנכתבו לפני שהיו הערות עשירות. שניהם נכתבים יחד בכל שמירה.

**הסינון מתבצע ביציאה, לא בכניסה.** `noteHtml` יכול להגיע מקובץ גיבוי שהתוסף
מעולם לא כתב, ולכן כל מסלול שהופך אותו חזרה ל-markup — כרטיס ברשימה, מילוי
העורך, ייצוא ל-HTML — מריץ `MarkerRichText.sanitize` מחדש. הסתמכות על "כבר
סיננו את זה כששמרנו" היא בדיוק ההנחה שקובץ גיבוי זדוני שובר.

השכבות מופרדות במכוון:

- **המדיניות** — אילו תגיות, אילו כתובות, אילו גדלי גופן — יושבת ב-
  `marker-domain.js` (`noteTagFor`, `safeNoteHref`, `safeNoteFontSize`). היא
  טהורה, ולכן `test/domain.test.js` בודק אותה מול רשימת התקפות: `<script>`,
  `<iframe>`, `javascript:`, `data:`, `java\tscript:`, `-moz-binding`, נתיב
  יחסי, ועוד.
- **ההפעלה** — הליכה על ה-DOM — יושבת ב-`marker-richtext.js`. הקלט נפרס
  ב-`DOMParser` (מסמך inert: סקריפטים אינם רצים, תמונות אינן נטענות), ולא
  ב-`innerHTML` של אלמנט חי.

בלי הפיצול הזה ה-sanitizer לא היה ניתן לבדיקה כלל: אין DOM ב-Node, והתוסף
מתחייב לאפס תלויות.

העורך עצמו נשען על `document.execCommand` להדגשה, נטוי, קו תחתי, קו חוצה,
כותרת, רשימות, ציטוט וקישור — כדי לקבל את התנהגות ה-undo המקורית של המנוע.
שני חריגים: `<mark>` מיושם ידנית דרך ה-Range API (ל-`hiliteColor` אין צורה
שה-allowlist יכול לסמוך עליה), וגודל הגופן נכתב כ-`font-size` מילולי אחרי
`styleWithCSS`. הדבקה עוברת דרך אותו sanitizer לפני שהיא נכנסת למסמך.

## i18n

עברית היא שפת המקור, וכל מחרוזת עברית משמשת גם כמפתח שלה. קטלוג הוא מפה שטוחה
מהמחרוזת העברית לתרגום.

- קוד: `t('הדגשות')`.
- HTML: `data-i18n` על האלמנט, או `data-i18n-attr="title,aria-label"` לתכונות.
  ה-HTML הסטטי נשאר עברית ו-`dir="rtl"` (ולידציית העיצוב דורשת זאת);
  `MarkerI18n.translateDocument` מתרגם בזמן ריצה ומחליף `lang`/`dir`.
- מקור השפה: בחירה מפורשת בהגדרות התוסף גוברת על שפת אוצריא. שינוי שפה בזמן
  ריצה מגיע ב-`settings.changed` עם המפתח `key-settings-language`.
- שמות הפריטים בתפריט ההקשר מתורגמים גם הם — `syncContributions` מעביר את `t`
  אל בוני ה-payload ב-`marker-domain.js`.

**כיסוי התרגום נאכף אוטומטית.** `test/i18n.test.js` סורק את כל קריאות `t()`
ואת כל סימוני ה-HTML, ונכשל אם מחרוזת חדשה חסרה בקטלוג האנגלי, אם נשאר בקטלוג
מפתח שכבר אינו בשימוש, אם תרגום איבד placeholder, או אם תרגום זהה למקור.
מחרוזת שמגיעה ל-`t()` דרך משתנה חייבת להירשם ב-`DYNAMIC_STRINGS` שב-
`test/helpers/i18n-strings.js`.

## גיבוי

- **אוטומטי**, במרחב הפרטי של התוסף (`fs.writeFile`, ללא הרשאה): `backups/latest.json`
  ועותק יומי, עם שמירת חמישה ימים אחרונים. מופעל בהשהיה של עשר שניות אחרי כל
  שינוי, כדי שעריכה מרוכזת לא תכתוב פעם לכל רשומה. רץ מכל מופע שביצע שינוי, לא
  רק מהמנוע — עריכות מהדף חייבות גיבוי בדיוק כמו סימון מהתפריט.
- **ידני**, לקובץ שהמשתמש בוחר: הבייטים עוברים ב-`fs.beginBinaryWrite` +
  `fs.commitUserFileWrite`, לא בגשר ה-JSON-RPC. זה גם המסלול היחיד שעובד בפועל
  ב-WebView של אוצריא — `window.open` מנוטרל שם והורדה דרך `<a download>` אינה
  אמינה.
- ייבוא שומר snapshot ומגלגל אחורה את ההדגשות וההגדרות אם משהו נכשל באמצע.
- `parseBackup` מקבל גם קבצי `schemaVersion: 1` מהגרסה הקודמת.

## דיווח למפתח

`feedback.report` שולח דיווח לאתר אוצריא, שמעביר אותו למפתח התוסף. הקריאה מנהלת
חסם זמן משלה וממתינה לדיאלוג האישור של אוצריא — **אין לעטוף אותה ב-timeout
מקומי**; ביטול מצד התוסף היה קוטע דיווח שהמשתמש באמצע אישורו. הקוד מוסיף
אוטומטית גרסת תוסף, גרסת אוצריא, פלטפורמה, שפה ומספר הדגשות. `feedback.hasReporterEmail`
נבדק מראש כדי לא לבקש כתובת שממילא תידרס.

## איפה לדבג

לוגים מתחילים ב-`[marker]` ונושאים את שם השכבה: `[marker][core]`,
`[marker][ui]`, `[marker][sdk]`, `[marker][events]`.

| התסמין | איפה לחפש |
|---------|-----------|
| הסימון לא נוצר | `[marker][core] Failed applying highlight`, ואחריו `MarkerSdkError.code` |
| התפריט לא מציג את הצבעים הנכונים | `syncContributions` ב-`marker-core.js`; בדקו אם `menuSignature` חסם עדכון |
| התפריט לא מופיע כלל | ההרשאה `app.startup_contributions` בהגדרות התוסף |
| לחיצה על צבע לא עושה כלום | שני מופעים חיים? בדקו `MarkerCore.isEngine` בשניהם |
| הדגשה נעלמה אחרי הפעלה מחדש | `reconcileHighlights` — האם `status` הוא `failed_to_anchor` |
| טקסט נשאר עברית באנגלית | חסר `data-i18n` ב-HTML, או מחרוזת שמגיעה ל-`t()` דרך משתנה |
| עיצוב בהערה נעלם בשמירה | ה-`sanitize` הוריד אותו — בדקו את `noteTagFor` / `safeNoteFontSize` |
| קישור בהערה לא נשמר | `safeNoteHref` מקבל רק `http`/`https` מוחלטים |
| „ייצוא ל-PDF” מחזיר `error.forbidden` | הקריאה לא יצאה ישירות מ-handler של לחיצה |
| „הסימון נכשל: אוצריא דחתה את הנתונים” | payload שאינו בחוזה — ראו „חוזה ה-payload” למעלה; ההודעה מ-`error.invalid_params` מציינת את השדה |
| „ערוך הערה” לא פותח כלום | ההדגשה אינה במאגר הדף; בדקו את `pendingEditId` ואת סדר ה-boot |

`MarkerSdkError` נושא `method`, `code`, `category`, `retryable` ו-`isUnsupported`.
`isUnsupported` הוא ההבדל בין "המארח הזה לא מכיר את הקריאה" (מדלגים) לבין כשל
אמיתי (מדווחים).

## בדיקות

```text
node --check js/marker-domain.js
node --check js/marker-i18n.js
node --check js/marker-runtime.js
node --check js/marker-core.js
node --check js/marker-ui.js
node --check i18n/en.js
node --test test/domain.test.js test/runtime.test.js test/core.test.js \
            test/i18n.test.js test/ui.test.js test/compatibility.test.js
git diff --check
```

| קובץ | מה הוא מכסה |
|------|--------------|
| `domain.test.js` | נרמול, עוגנים, תפריט, סינון, מיון, גיבוי, ומדיניות סינון ההערות — הכול טהור |
| `runtime.test.js` | מעטפת ה-SDK, `isUnsupported`, התור הסדרתי |
| `core.test.js` | המנוע מקצה לקצה מול host מדומה: תרומות, סימון, הסרה, שחזור, הרשאות, שפה |
| `i18n.test.js` | כיסוי תרגום מלא ואכיפת placeholders |
| `ui.test.js` | חוזה סטטי של הדף: ids, מחלקות CSS, סדר טעינה, נגישות |
| `compatibility.test.js` | מניפסט מול קוד: גרסאות API, הרשאות, תרומות, שכבות, escaping |

`test/helpers/harness.js` מדמה את ה-host: מעטפת ה-RPC, אחסון, רישום ההדגשות
ורישום תפריט ההקשר — כולל העובדה שהמניפסט כבר רשם את הפריטים, ולכן המסלול הרגיל
הוא `update` ולא `add`.

הבדיקות אינן מריצות DOM. הרצה בתוך אוצריא נשארת חובה לפני שחרור; הרשימה
ב-[CONTRIBUTING](../CONTRIBUTING.md).
