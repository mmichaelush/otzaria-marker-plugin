# ארכיטקטורת תוסף המרקר

מסמך תחזוקה. מי שרוצה להבין מה התוסף עושה — [מדריך המשתמש](USER_GUIDE.md);
מי שרוצה לדעת על איזו גרסת אוצריא הוא נשען — [COMPATIBILITY](COMPATIBILITY.md).

## תמונה כללית

התוסף בנוי סביב הפרדה אחת מרכזית: **מה שנרשם באוצריא בלי שום קוד JS** מופרד
ממה שדורש מנוע חי.

```
manifest.json          תרומות דקלרטיביות: תפריט הקשר, פקד סרגל, קיצורי מקשים
  │                    אוצריא קוראת אותן ב-Dart בעליית התוכנה, בלי מנוע JS
  ├─► background.html   domain → i18n → en.js → runtime → core → background
  │                     המנוע. בלי DOM, בלי CSS, חי כל עוד אוצריא פתוחה
  └─► index.html        domain → i18n → en.js → runtime → richtext → core → ui
                        הדף. מציג, עורך, מייצא — ומצייר עותק משלו
```

| קובץ | אחריות | מה אסור בו |
|------|---------|-------------|
| `js/marker-domain.js` | כללי דומיין טהורים: נרמול, טווחים, בניית payloads, סינון ומיון | DOM, SDK, timers |
| `js/marker-i18n.js` | קטלוג תרגום, בחירת שפה, תרגום ה-DOM | לוגיקה עסקית |
| `js/marker-runtime.js` | הגבול היחיד מול ה-SDK: `call`, שגיאות, לוגר, תור, הגנת אירועים | DOM, כללי דומיין |
| `js/marker-richtext.js` | עורך ההערות וה-sanitizer שמפעיל את מדיניות הדומיין | SDK, כללי דומיין |
| `js/marker-core.js` | המנוע: הגדרות, מאגר ההדגשות, התרומות, החלת/הסרת סימון, גיבוי, דיווח | DOM |
| `js/marker-ui.js` | הדף בלבד: rendering, טפסים, דיאלוגים | קריאת SDK ישירה, כללי דומיין |
| `js/marker-background.js` | שורה אחת: `MarkerCore.start()` ב-`background.html` | כל דבר אחר |
| `i18n/en.js` | קטלוג אנגלית. המפתחות הם מחרוזות המקור בעברית | — |

הגבולות האלה אינם המלצה: `test/compatibility.test.js` נכשל אם `marker-domain.js`
נוגע ב-DOM, אם מודול כלשהו קורא ל-`Otzaria.call` ישירות, או אם `marker-core.js`
מזכיר את ה-DOM.

## בעלות על ההדגשות

**כל מופע מצייר, ואוצריא מציגה את האיחוד פעם אחת.**

אוצריא מחזיקה בעלות על הדגשות **לפי מופע**, לא לפי תוסף:
`PluginHighlightRegistry` ממפתח כל רשומה ב-`(pluginId, instanceId)`, ולכן
`getHighlights`, `updateHighlight` ו-`clearHighlight` של מופע אחד אינם רואים
את הרשומות של מופע אחר כלל. `PluginBridgeAdapter.dispose` קורא
ל-`removeInstance`, וכל סימון שאותו מופע צייר נמחק איתו.

**אבל שכבת הציור מאחדת.** `getAllHighlights` עושה dedup לפי
`(ownerPluginId, highlightId)` — לא לפי תוכן — ומעדיפה את העותק של מופע גלוי.
כלומר אותו סימון שמוחזק בידי ארבעה מופעים מצויר **פעם אחת**, והעותק של המופע
שהמשתמש מסתכל בו הוא שמנצח. זה בדיוק מה שהמנגנון נבנה בשבילו, וזה מה שהופך
"כל אחד מצייר" לזול ולנכון.

בחירת מופע יחיד שמצייר הייתה הטעות היקרה ביותר בתוסף הזה. בכל פעם שהבחירה
הייתה שגויה — המנוע כובה אחרי שלוש דקות, ההרשאה נדחתה, הלחיצה נותבה למופע אחר —
**לא צויר כלום**, ושום דבר לא הסביר למה. עותק מיותר עולה קריאת RPC אחת; עותק
חסר עולה את הפיצ'ר.

עד גרסה 0.9.5 המופע היחיד היה **דף התוסף**, ומכאן שני באגים שהמשתמשים דיווחו
עליהם:

1. הסימונים הופיעו בספר רק כשלשונית התוסף הייתה פתוחה ברקע. ברגע שהיא נסגרה
   ה-Host מחק את כל ההדגשות של אותו מופע מהדף.
2. לחיצה על צבע בתפריט הימני כשהתוסף לא היה פתוח **פתחה את דף התוסף** במקום
   לסמן. זו התנהגות מתועדת של ה-Host: בלי `app.run_on_startup` לחיצה על תרומה
   דקלרטיבית נופלת לפתיחת דף התוסף, כדי שהפעלת קוד תוסף תהיה תמיד גלויה.

מגרסה 0.9.6 יש מנוע רקע לצד הדף, וזה ההבדל ביניהם:

| | מנוע הרקע (`background.html`) | הדף (`index.html`) |
|---|---|---|
| `MarkerDomain.ownsEngine` | `true` | `false` |
| מצייר בקורא | כן | כן — עותק משלו, שמאוחד בציור |
| רושם תרומה חדשה (`addContextMenuItem`) | כן | לא — רישום נקשר למופע הרושם |
| מקבל לחיצות תפריט, סרגל וקיצורים | כן (`preferBackground: true`) | כשאין מנוע חי, ואז הוא מטפל בהן במלואן |
| חי | כל עוד אוצריא פתוחה | כל עוד הלשונית פתוחה |

`ownsEngine` אינו מחליט מי מצייר — הוא מחליט מי רשאי **לרשום** תרומה שאינה
במניפסט, כי `addContextMenuItem` נקשר למופע הקורא.

שלושה דברים מחזיקים אותו, ואם אחד מהם יורד הבאג חוזר:

- `contributes.background.entrypoint` — קובץ כניסה נטול UI. בלעדיו אוצריא
  הייתה טוענת את `index.html` כולו ב-WebView נסתר.
- `contributes.startup.activationEvents` — מה שמעיר אותו. ההרשאה לבדה אינה
  מרימה מנוע. הרשימה היא `reader.current_ref_changed` ו-
  `reader.sectionContentChanged`, ו-**`app.startup` אינו בה בכוונה** (ראו
  למטה).
- `startup.keepAlive: true` + ההרשאה `app.background_keep_alive` — בלעדיהן
  אוצריא מכבה מופע רקע עצל אחרי כשלוש דקות, **וההדגשות נמחקות איתו**. זו
  הרשאה רגישה שהמשתמש מאשר בנפרד; `showEngineNotice` בדף מסביר בדיוק מה
  יקרה בלעדיה.

`test/compatibility.test.js` אוכף את שלושתם.

### למה זה חשוב דווקא כשאין מנוע

`app.background_keep_alive` היא הרשאה אדומה שמשתמשים ידחו, ובלעדיה אוצריא
מכבה את מנוע הרקע אחרי כשלוש דקות של חוסר פעילות. מאותו רגע, כל עוד לשונית
התוסף פתוחה, **הלחיצות מגיעות לדף**: `dispatchEventToPlugin` נקראת עם
`preferBackground: true`, ומעדיפה את הרקע רק כשהוא קיים.

כשהדף צייר בעצמו, זה עובד. כשהוא סירב לצייר "כי הוא לא המנוע", הסימון נשמר,
הופיע ברשימה, לא הופיע בספר, ונשאר כך עד הפעלה מחדש של אוצריא.
`test/two-instances.test.js` שומר בדיוק על המקרה הזה.

### שני חלונות של אוצריא

אוצריא פותחת חלון כתהליך משלו (`main` → `secondaryWindowMain`), ולכן **לכל
חלון יש `PluginHighlightRegistry`, `ContextMenuRegistry` ו-`PluginRuntimeDispatcher`
משלו, ומנוע רקע משלו.** הם singletons per-isolate, לא per-process-group.

מה שמשותף בין חלונות הוא דבר אחד: אחסון התוסף, טבלת KV ב-SQLite על הדיסק. זה
בדיוק מה שאסימון ה-`REVISION_KEY` רוכב עליו, ולכן אותו מנגנון שמיישר שני
מופעים מיישר גם שמונה.

מה שנובע מזה, ומה ש-`test/multi-window.test.js` אוכף:

- **כל חלון חייב לצייר בעצמו.** רשומה שצוירה ב-registry של חלון אחד אינה קיימת
  אצל השני. מודל של "מופע אחד מצייר לכולם" היה משאיר כל חלון נוסף ריק.
- **מחיקה, שינוי צבע והסתרת ספר מתפשטים** — דרך האחסון המשותף, תוך מחזור דגימה
  אחד (עד 1.5 שניות).
- **סגירת חלון אינה נוגעת באחרים.** ה-Host מוחק את הרשומות של המופעים שנסגרו
  בלבד, וסריקת היתומים ב-`reconcileHighlights` נוגעת רק ברשומות של המופע
  שמריץ אותה.
- **`version` ו-`etag` אינם נשמרים לאחסון.** הם שייכים לעותק של מופע מסוים,
  ושמירתם גרמה לחלונות לדרוס זה את מספריו של זה בכל סבב, עבור ערך שאיש מהם
  אינו קורא בחזרה.
- **דגל הפקד בסרגל נכתב בכל חלון בנפרד.** `PluginConditionEvaluator` מחזיק
  snapshot בזיכרון ומרענן אותו רק בחלון שכתב; חלון שלמד על השינוי מהאחסון
  כותב את מה שקרא, וכך מרענן את המעריך שלו. כתיבה של אותו ערך אינה שינוי,
  ולכן אין פינג-פונג.

### איך שני המופעים מסתנכרנים

אין ערוץ הודעות בין מופעי תוסף, ואין אירוע על כתיבה לאחסון. לכן:

- **הדף אינו קורא ל-`reader.revealHighlight`** בשביל מופע אחר — היא
  per-instance. כל שאר הסנכרון בין מופעים עובר ב-`storage` ובאסימון
  `MarkerDomain.REVISION_KEY`, שכל כתיבה מחדשת.
- **כל מופע דוגם את האסימון** (`pollRevision`, אחת ל-1.5 שניות — קריאת
  `storage.get` אחת של מחרוזת קצרה). כשהוא שונה ממה שהמופע כתב בעצמו, הוא טוען
  מחדש הגדרות, ספרים מושתקים והדגשות; המנוע גם מסנכרן את התפריט ומצייר מחדש.
  אסימון ולא מונה, כי מונה הוא read-modify-write: שני מופעים שמגדילים את אותו
  ערך היו נוחתים על אותו מספר, וכל אחד היה מסיק שכלום לא השתנה.
- **פתיחת הדגשה מהרשימה עוברת ב-`reader.scrollToSection`.**
  `reader.revealHighlight` היא per-instance ולכן אינה זמינה לדף, ו-
  `openBookAtRef` מנווט ל-`ref` — כלומר לפרק או לסימן, לא לשורה. בהדגשה
  באמצע פרק ארוך זה נחת בראש הפרק. `scrollToSection` אינה דורשת בעלות,
  מקבלת את `sectionIndex` שהרשומה כבר נושאת, ומדויקת לשורה; היא מנוסה שלוש
  פעמים כי היא מחזירה `false` כל עוד חלונית הקריאה עדיין נבנית.
- **`reconcileHighlights` משווה גם סגנון.** שינוי צבע בדף אינו יכול לגעת
  ברשומת ה-Host של המנוע, ולכן המנוע מזהה שמה שמצויר אינו תואם למה ששמור,
  ומצייר מחדש.

בלי הרשאת `app.run_on_startup` אין מנוע רקע להסתמך עליו, ואז `ownsEngine`
מחזיר `true` גם לדף — התוסף חוזר בדיוק להתנהגות של 0.9.5, ולא לשום דבר גרוע
ממנה.

**עדכון תפריט ההקשר מותר מכל מופע.** פריטי התפריט רשומים ברמת התוסף (מהמניפסט),
ולכן `reader.updateContextMenuItem` מעדכן את אותה רשומה ומה שמעודכן שורד את
סגירת הדף. **רישום** פריט חדש (`add`) הוא מסלול נפילה בלבד — רישום נקשר למופע
הרושם, והוא גם מה שקובע לאן אוצריא מנתבת את הלחיצה
(`pickContributionTarget`): כל עוד הרישום נשאר ברמת התוסף, הלחיצה מגיעה למנוע
הרקע גם כשהדף פתוח.

## תפריט ההקשר — למה הוא דקלרטיבי

`contributes.startup.contextMenuItems` במניפסט רושם שני פריטים עוד לפני שקיים
מנוע JS:

| id | סוג | הקשר | תפקיד |
|----|-----|------|--------|
| `marker-colors` | `color-row` או `submenu` | `reader-selection`, `reader-page-shape-selection` | בחירת צבע לסימון |
| `marker-highlight-actions` | `submenu` | `reader-highlight` | פעולות על הדגשה קיימת |

הפריט השני הוא תת-תפריט ולא שני פריטים, מפני שהמכסה היא שני פריטים עליונים
לתוסף ושורת הצבעים תופסת אחד. ילדיו:

| id | פעולה | הערה |
|----|--------|-------|
| `marker-note` | ערוך הערה | `openPlugin: true` — רק הדף יכול להציג עורך |
| `marker-remove` | הסר סימון | פועל headless, בלי לפתוח את הדף |

ופקד אחד בסרגל מסך העיון:

| id | פעולה | הערה |
|----|--------|-------|
| `marker-toolbar` | הסתרה/הצגה של ההדגשות בספר הפתוח | **אין `openPlugin`.** לחיצה אחת אמורה לפעול במקום שבו המשתמש נמצא, לא לזרוק אותו ללשונית אחרת. הפקד מותנה ב-`when: { storage: { key: 'marker_toolbar_button', notEquals: false } }`, כך שהמשתמש יכול להסיר אותו מהסרגל בלי שום קוד תוסף שרץ |

הדגל `marker_toolbar_button` יושב במפתח אחסון משלו ולא בתוך `marker_settings`,
מפני ש-`when` של ה-Host משווה **ערך שמור שלם** ואינו יודע להיכנס לתוך אובייקט.
`MarkerCore.syncToolbarFlag` מחזיק אותו בסנכרון עם ההגדרה שהמשתמש עורך.

### לחיצות אינן מותנות בבעלות על המנוע

**זו הייתה תקלה אמיתית, ושווה לזכור אותה.** אוצריא מוסרת אירוע *ממוקד* —
לחיצה על פריט תפריט, על פקד סרגל, או קיצור מקלדת — למופע **אחד בלבד**
(`dispatchEventToPlugin` בוחר controller יחיד). לעומת זאת אירוע *שידור*
(`reader.sectionContentChanged`, `settings.changed`) מגיע לכל המופעים החיים
(`dispatchEvent`, לולאה על `targetControllers`).

מכאן:

- **מטפלי לחיצה אינם בודקים `isEngine`.** אין כפילות למנוע. הבדיקה גרמה לכך
  שאוצריא ניתבה לחיצה למופע שה-`isEngine` שלו `false` — והלחיצה נעלמה בלי
  שגיאה בשום מקום. לחיצה על צבע פשוט לא עשתה כלום.
- **מטפלי שידור כן בודקים `isEngine`**, אחרת אותה עבודה תרוץ פעמיים.

לחיצה עשויה להיות מה שהעיר את המופע, ואז היא נמסרת מיד אחרי שיגור
`plugin.boot` — בזמן שה-handler שלנו עדיין קורא מהאחסון. לכן כל מטפל לחיצה
ממתין ל-`whenBooted()` לפני שהוא נוגע ב-`settings`.

זה מה שמאפשר לתפריט לעבוד מהשנייה הראשונה של אוצריא, בלי שהתוסף עלה. הצבעים
במניפסט הם ברירות המחדל; כשהמנוע מתעורר הוא **מעדכן** את הפריט
לצבעים ולשפה של המשתמש דרך `reader.updateContextMenuItem`. `reader.addContextMenuItem`
הוא מסלול נפילה בלבד — למקרה שההרשאה `app.startup_contributions` בוטלה.

### המחק בשורת הצבעים

הסרת סימון זמינה בשני מקומות, ולא במקרה. `marker-remove` יושב בהקשר
`reader-highlight`, וה-host בונה את ההקשר הזה רק כשהלחיצה הימנית נופלת בדיוק
על סימון **וגם אין בחירה פעילה** (`_buildClickedHighlightEntries`). מיד אחרי
סימון בדרך כלל *יש* בחירה, ולכן התפריט הולך למסלול `reader-selection` —
שבו, עד גרסה 0.9.5, לא היה שום מחק. הפעולה הייתה קיימת ובלתי נגישה.

לכן שורת הצבעים נגמרת בערך `mark-clear`: `color: '#00000000'` (שקוף מלא, כך
שה-host מצייר את האייקון במקום גוש צבע) עם
`icon: 'eraser_24_regular'` — המחק של פלואנט, אותו גליף שאוצריא מציגה בתפריט
ההדגשות שלה עצמה. לחיצה עליו מסירה כל סימון שנוגע בבחירה — חפיפה ולא הכלה, כי מי שגורר בערך מעל סימון מצפה שהוא ילך.

`toSafeHex` נעקף עבור הערך הזה בכוונה: הוא שומר שש ספרות hex והיה הופך את
השקוף לשחור אטום.

**המחק מופיע רק כשיש מה למחוק, תמיד — זו אינה הגדרה.** ל-Host אין תנאי
„הבחירה חופפת להדגשה” (`showWhen` יודע להשוות מילים בלבד), ולכן התוסף מחזיק
את הרישום מסונכרן עם הבחירה בעצמו: `reader.selection_changed`, דיבאונס של
120ms, ו-RPC רק כשהתשובה באמת התהפכה (`eraserInMenu`).

**ל-`reader.selection_changed` אין עוגן, וזו הסיבה שהניסיון הראשון לא עבד
בכלל.** ה-payload שלו הוא הצורה הישנה — `text`, `currentRef`,
`currentBookId`, `currentIndex` וזהות הספר — בלי `sourceRange` ובלי
`sections`. בדיקת חפיפה על טווחים לא מצאה טווחים, ולכן ענתה תמיד „לא”.
`MarkerDomain.selectionTouchesHighlight` היא השער: חפיפה מדויקת כשיש עוגנים
(ה-payload של תפריט ההקשר), ואחרת רמת מקטע — „מקטע שיש בו סימון”, שזו גם
הדרישה כפי שנוסחה.

**המטפל אינו מגודר ב-`isEngine`, וזו הנקודה שנשברה בפעם הראשונה.**
`reader.selection_changed` הוא אירוע שידור, ו-
`PluginRuntimeDispatcher._selectEventTargets` מוסר שידור למופעים הקדמיים
החיים כשיש כאלה — ונופל למנוע הרקע רק כשאין אף אחד. כלומר: **כל עוד לשונית
התוסף פתוחה, מנוע הרקע אינו רואה בחירות בכלל.** עם הגדר על `isEngine` אף אחד
לא עדכן את התפריט, והמחק נתקע במצב שבו היה עד הפעלה מחדש של התוסף. עדכון
פריט תפריט מותר מכל מופע (הרישום ברמת התוסף), ולכן הדף עושה את זה בעצמו.

כשההרשאה `events.subscribe:reader.selection_changed` אינה מאושרת אי אפשר
לדעת מה מסומן, וכלל של „רק מעל סימון” היה אומר „לעולם לא”. במקרה הזה המחק
נשאר בשורה לתמיד (`eraserFollowsSelection`) — תפריט מעט עמוס הוא כשל טוב
בהרבה מפעולה שאי אפשר להגיע אליה.

### שתי מגבלות של המארח בשורת הצבעים

1. **הכותרת אינה מוצגת, בשום רוחב.** `AppContextMenuEntry.colorRow` במארח
   מקבל רשימת צבעים בלבד וקובע `label = null` בבנאי; ה-`title` שהתוסף שולח
   נזרק. זו אינה בעיית מקום. מי שרוצה לראות „מרקר” בתפריט בוחר בסגנון
   תת-תפריט, שכן מציג שם ואייקון. אין לפצל את הכותרת לפריט עליון נפרד —
   המכסה היא שני פריטים, והשני תפוס בפעולות על הדגשה.
2. **`selected` מצויר כטבעת עבה בצבע ה-primary** (3px), ולא כסימון עדין.
   סימון צבע ברירת המחדל בדרך הזו נראה כתקלת רינדור, ולכן התוסף אינו שולח
   את השדה.

`MarkerDomain.menuSignature` חוסם עדכון מיותר: הפונקציה מקודדת רק את מה שהתפריט
באמת מציג (סגנון, צבעים פעילים, שמות, שפה), כך ששינוי גודל גופן אינו גורם
לקריאת RPC.

### מה נעלם ביחס לגרסה הקודמת

בגרסה 0.9.x התוסף עקב אחרי `reader.selection_changed`, שמר את הבחירה האחרונה,
פענח בעצמו בחירה רב-שורתית עם `reader.findTextOccurrences`, והוסיף/הסיר את פריט
"הסר סימון" מתוך שורת הצבעים בכל שינוי בחירה. כל זה נמחק:

- **`selection.sections`** (0.9.97) — אוצריא מעגנת בעצמה כל פסקה בבחירה
  רב-פסקתית ומוסרת אותה ב-payload של הלחיצה. אין יותר ניחוש עוגנים.
- **הקשר `reader-highlight`** (0.9.97) — "הסר סימון" הוא פריט נפרד שאוצריא מציגה
  רק כשלוחצים על הדגשה בפועל, עם `selection.clickedHighlights`. אין יותר בדיקת
  חפיפה בכל שינוי בחירה כדי *לבצע* מחיקה, ואין מכונת המצבים של `savedSelection`
  / `selectionRevision` / `queueMenuTask`.
- `events.subscribe:navigation.changed` אינה נדרשת יותר.

שתי הרשאות מהרשימה ההיא כן חזרו ב-0.9.6, לתפקידים צרים ומדודים:
`reader.selection_changed` מחליט אם המחק נמצא בשורת הצבעים, ו-
`reader.current_ref_changed` מחזיק את תווית הפקד בסרגל מעודכנת ומעיר את מנוע
הרקע אם הוא כובה.

## שם ה׳

התוסף מציג את הטקסט המסומן כפי שהספר מציג אותו, כולל החלפת שם הוי"ה.
`MarkerDomain.replaceHolyNames` הוא פורט של `replaceHolyNames` מאוצריא
(`lib/utils/text/text_manipulation.dart`) — אותו רגקס, אותה בדיקת „שלוש אותיות
עבריות לפני ההתאמה” שמונעת החלפה ב„ויגביהוהו”, ואותם שני סגנונות (`kuf`,
`heh`).

- המדיניות מחושבת ב-`resolveHolyNamePolicy` משתי הגדרות: `settings.holyNames`
  של התוסף (`auto` / `always` / `never`) ושל אוצריא
  (`key-replace-holy-names`, `key-holy-name-style`, נקראות ב-`settings.getMany`).
- **ההחלפה היא בתצוגה בלבד.** הרשומה שמורה בנוסח הספר, כך שכיבוי ההגדרה מחזיר
  אותו וייצוא אינו מקבע העדפת תצוגה של קורא אחד בתוך הנתונים.
- החיפוש מוצא את שתי הצורות: `highlightHaystack` מקבל גם את הטקסט המוצג.

## גופנים

התוסף אינו אורז קובצי גופן. `src: local()` ב-WebView של תוסף פותר רק גופנים
מותקנים במערכת ולעולם לא את אלה שאוצריא מזריקה, ולכן עד 0.9.5 נארזו כאן תשע
משפחות שהמשתמש כבר מחזיק. `fonts.resolveFamilies` (0.9.97) מחזיר כללי
`@font-face` עם הבייטים של אוצריא תחת השם שביקשנו; `READING_FONTS`
ב-`marker-ui.js` מחזיק את סדר התחליפים, והטעינה עצלה — רק כשהמשתמש בוחר
משפחה.

## מחזור החיים של ההדגשות

הדגשות חיות בשני מקומות: `storage` של התוסף (מתמיד) והזיכרון של אוצריא (נמחק
בכל הפעלה מחדש). `reconcileHighlights()` הוא הפעולה שמיישרת ביניהם, וזו אותה
פעולה גם בעלייה קרה וגם בהתעוררות חמה:

1. קריאה אחת ל-`reader.getHighlights({ includeStale: true })`.
2. רשומה שאינה אצל ה-Host — מצוירת מחדש (`reader.setHighlight`).
3. רשומה שהסגנון המצויר שלה אינו תואם לסגנון השמור — מצוירת מחדש. זה המסלול
   היחיד שדרכו שינוי צבע שנעשה בדף מגיע לספר, כי הדף אינו יכול לגעת ברשומה
   של המנוע.
4. רשומה שקיימת אך `version` / `etag` / `status` / `range` שלה זזו — נשמרת מחדש.

בעלייה קרה זה אומר ציור של הכול; בהתעוררות חמה זו קריאה אחת בלי אף כתיבה.
רשומה של ספר מושתק (ראו למטה) מדולגת לגמרי.

**קריאה שנכשלה אינה אחסון ריק.** `reconcileHighlights` מוריד סימונים מהדף לפי
ההפרש בין מה שמצויר למה ששמור, ולכן מותר לו לעשות זאת רק כשהוא יודע שקרא את
האחסון כולו. `loadHighlights` מסמן את זה ב-`storeComplete`, ובקריאה חלקית —
`storage.list` שנכשל, `storage.get` בודד שנכשל — סבב הניקוי מוותר על עצמו. בלי
הכלל הזה תקלת קריאה אחת מוחקת למשתמש את הסימונים מול העיניים, בלי שנמחק דבר
מהאחסון ובלי שום הודעה. אותו דין ל-`reader.getHighlights`: בלי לדעת מה מצויר,
הסבב מוותר במקום לצייר הכול מחדש על סמך תשובה ריקה.

**ולכלל יש חצי שני, בלעדיו הוא מזיק:** `pollRevision` מנסה לקרוא שוב כל עוד
`storeComplete` הוא `false`, גם כשהאסימון לא זז. הוויתור על המחיקה לבדו רק הפך
את הנזק לקבוע — האסימון לא השתנה, הדגימה חזרה מיד בכל תקתוק, והרשומה שלא נקראה
נשארה חסרה מהרשימה ומהדף עד הפעלה מחדש של אוצריא. מאותה סיבה `deleteAllHighlights`
מסרבת לפעול על תמונה חלקית: היא הייתה מוחקת רק את מה שהצליחה לקרוא, ומודיעה
שהכול נמחק.

### מגביל הקצב של אוצריא — הנקודה שהכי קל למעוד בה

`PluginBridgeHandler.RateLimiter` הוא דלי של **50 טוקנים** שבכל קריאה מוסיף
`elapsed ~/ 10` טוקנים — ומיד מקדם את `lastRefill` ל-`now`, כלומר **זורק את
השארית**. המשמעות אינה האטה מתונה אלא מצוק: רצף קריאות בפער קטן מ-10ms אינו
ממלא כלום, ולכן בדיוק 50 עוברות וכל השאר חוזרות `error.rate_limited` עד שהתוסף
שותק לרגע. זה נכון בלולאת `await` סדרתית בדיוק כמו ב-`Promise.all` — קריאת
אחסון נענית הרבה מתחת ל-10ms.

50 הוא מספר קטן כאן: קריאה של 200 הדגשות שמורות היא 200 קריאות, וציורן אחרי
עלייה קרה עוד 200. משתמש עם כמה עשרות סימונים חצה את התקרה בכל עלייה.

וכל סירוב היה שקט: `storage.get` שנבלע נראה בדיוק כמו הדגשה שמעולם לא נשמרה,
`reader.setHighlight` שנבלע כמו סימון שהמשתמש לא עשה, ו-`ui.showError` שנבלע
הוא הסיבה שגם לא הייתה הודעת שגיאה על אף אחד מהם.

לכן `MarkerRuntime.callRaw` מחזיק **עותק של אותו דלי** וממתין במקום להיענות
בסירוב. הדלי של המארח שייך ל-WebView ולא לתוסף — `PluginBridgeHandler` אחד לכל
מופע — ולכן העותק שלנו הוא של הדבר הנכון. מה שהוא לא יכול להיות זה מדויק: הוא
מתחיל לספור כשהסקריפט נטען ולא כשה-WebView נרשם, המארח גובה טוקן גם על קריאות
שאיננו עושים (שיטה לא מוכרת, קריאה מ-iframe), ו-`Date.now()` שלנו גס מזה של
Dart. לכן העותק מתחיל ב-45 ולא ב-50, וההפרש הוא כרית לסחיפה.

מעליו יש ניסיון חוזר, אך **רק ל-`error.rate_limited`**: זו התקלה היחידה שהמארח
מרים לפני שהריץ את הקריאה בכלל, ולכן חזרה עליה בטוחה בכל שיטה, גם כזו ששולחת
דואר או כותבת קובץ. `error.timeout` אינו חוזר — שם העבודה אולי כן קרתה.

בנוסף, `MarkerRuntime.mapLimit` מחליף כל `Promise.all` על רשימה שאורכה נקבע
בידי המשתמש. `test/rate-limit.test.js` מריץ את כל זה מול נמל של המגביל האמיתי.

### הסתרה זמנית של ספר

הפקד בסרגל, הקיצור `Ctrl+Alt+J` ו-`MarkerCore.toggleMutedBook` עושים את אותו
דבר: מוסיפים או מוציאים `bookId` מ-`MUTED_BOOKS_KEY`, ואז
`reader.clearAllHighlights({ bookId })` או ציור מחדש של אותו ספר. **שום דבר
אינו נמחק** — הרשומות נשארות ב-`storage` וברשימה, והן פשוט אינן מצוירות. הרשימה
נשמרת באחסון ולא בזיכרון, כדי ש"הסתרתי את הספר הזה" ישרוד פינוי של מופע הרקע.

`normalizeHighlight` הוא השער היחיד לרשומה: הוא מוחק שדות לא מוכרים, פוסל רשומה
בלי עוגן שמיש, ומחזיר תמיד את אותו מבנה. רשומה פגומה מדולגת ולא מפילה את הטעינה.

### חוזה ה-payload של ה-Host

`reader.setHighlight` אינו סובלני: הוא דוחה שדה לא מוכר, ערך מחוץ לרשימה
סגורה, וטווח מספרי חורג. הנקודה שהכי קל להיכשל בה היא `metadata.source` —
ה-Host מקבל **רק** `manual`, `ai`, `import` או `sync`. ערך אחר מוחזר כ-
`error.invalid_params: unsupported highlight source`, ואף הדגשה אינה נוצרת.
לכן כל ה-metadata נבנה בנקודה אחת, `MarkerDomain.buildHighlightMetadata`,
שגם חותכת את התגיות לפי מגבלות ה-Host (עד 20, עד 64 תווים, בלי ריקות).

**ה-harness אוכף את החוזה הזה.** `test/helpers/harness.js` מחקה את
`PluginHighlightRegistry` ואת `ContextMenuRegistry`: allowlist של שדות, ערכים
סגורים, טווחים, ופרסינג מחדש של פריט תפריט **אחרי המיזוג** של ה-patch. זו לא
קפדנות לשמה — גרסה קודמת שלחה `source: 'marker'`, כל הדגשה נכשלה באפליקציה,
וכל הבדיקות עברו בירוק מפני שה-fake קיבל כל דבר.

### חוזה הרשומה

```
highlightId  groupId  bookId  bookUid  book  sectionIndex
colorId  color  style  text  ref  note  tags  favorite
sourceRange  version  etag  status  timestamp
```

- מפתח האחסון הוא `highlight:<highlightId>` — `isSafeHighlightId` מוודא שהמזהה
  אינו יכול לצאת מהמרחב.
- `groupId` משותף לכל חלקי בחירה רב-פסקתית. חלקים כאלה תמיד נמחקים יחד
  (`expandByGroup`).
- `bookUid` הוא המזהה היציב שאוצריא ממליצה לשמור. `book` נשמר לצדו כ-fallback
  חינני, כפי שהתיעוד דורש.

## מחזור החיים של שני המופעים

**מנוע הרקע** עולה ברגע שהקורא מדווח על מיקום — `reader.current_ref_changed`
או `reader.sectionContentChanged` — כלומר מהרגע שיש ספר על המסך, וזו בדיוק
השעה שבה הוא נחוץ. הוא טוען הגדרות, ספרים מושתקים והדגשות, מסנכרן את התרומות
ומצייר הכול, ואחר כך נשאר חי (`keepAlive`) ומטפל בלחיצות, בקיצורים ובאירועי
הקורא. אם ההרשאה `app.background_keep_alive` כבויה הוא מכובה אחרי כשלוש דקות
של חוסר פעילות וההדגשות יורדות איתו; אותם `activationEvents` מעירים אותו שוב
בניווט הבא.

### למה `app.startup` אינו ברשימה — ואסור להחזיר אותו

הוא נעל את התוסף לחלוטין: לא סימון, לא מחיקה, לא פקד ולא קיצור, בלי שום שגיאה.

`PluginLazyActivationService.syncPlugin` דורך על `app.startup` שעון חד-פעמי של
שמונה שניות שקורא ל-`_activate` **בלי לבדוק אם כבר רץ מנוע**. `_activate` מסמן
`_activating[pluginId]` וקורא ל-activator, ו-`PluginBackgroundHost._activateOnDemand`
יוצא מיד — בהצלחה, בלי לבנות דבר — כי `_activeBackgroundPlugins` כבר מחזיק את
התוסף. בלי widget אין `onLoadStop`, ולכן לא נקראת `onBackgroundInstanceReady`
ולא `onBackgroundInstanceFailed`; `_activating` נשאר דלוק לנצח ו-`isBootPending`
מחזיר `true` לתמיד.

ומכאן זה קטלני: `dispatchEventToPlugin` בודקת `queueIfBootPending` **לפני**
שהיא מחפשת controller, ולכן מאותו רגע כל אירוע ממוקד — לחיצת צבע, לחיצת פקד,
קיצור — נכנס לתור שאיש לא ירוקן, גם כשלשונית תוסף בריאה לגמרי פתוחה. שידורים
ממשיכים לזרום כרגיל, ולכן זה נראה כאילו התוסף חי אבל חירש. ביומן זה נראה כך:

```text
PluginRuntimeDispatcher: contextMenu.colorClicked → queued (boot pending)
PluginRuntimeDispatcher: reader.toolbar_item_clicked → queued (boot pending)
PluginRuntimeDispatcher: Dispatching reader.selection_changed
```

אם המלכודת נסגרת תלוי רק בשאלה אם המנוע במקרה כבר היה למעלה בשנייה השמינית —
ולכן זה נקרא "עובד כמה שניות ואז נתקע". סימון אחד בשניות הראשונות מעיר את
המנוע, ושמונה שניות אחר כך השעון יורה לתוך מנוע בריא והורג את הכול. לשונית
תוסף פתוחה־אך־מושהית מזרזת את זה: מופע מושהה אינו "שמיש", ולכן
`reader.current_ref_changed` מעיר את המנוע כבר בשנייה הראשונה.

לא מפסידים מזה כלום. שאר הטריגרים הם אירועי קורא, והם נורים ברגע שיש ספר על
המסך. כל שאר המסלולים אל `_activate` מגודרים ב"אין מופע שמיש", ולכן רק השעון
הזה יכול היה לירות לתוך מנוע חי.

`test/compatibility.test.js` אוכף שהוא אינו חוזר.

**הדף** עולה כשהמשתמש פותח את לשונית התוסף, וגם כשאוצריא מעירה אותו בעקבות
`marker-note`. בכל עלייה הוא טוען את ההדגשות מהאחסון — האחסון הוא המצב
הסמכותי, לא מה שמצויר — ומיישר מולו את מה שהוא עצמו מצייר (`reconcileHighlights`).

`reader.sectionContentChanged` נשמר כמנוי כדי שהמנוע יגיב מיד לשינוי נוסח.
`plugin.resumed` מפעיל `pollRevision` מיד: אוצריא מקפיאה לשונית תוסף שאינה על
המסך, כך שגם שעון הדגימה לא רץ בזמן הזה.

לחיצה עשויה להיות מה שהעיר את המופע, ולכן היא נמסרת מיד אחרי `plugin.boot` —
בזמן שהאחסון עדיין נקרא. כל מטפל לחיצה ממתין ל-`whenBooted()` לפני שהוא נוגע
ב-`settings`.

## הערות עשירות — ואיפה גבול האבטחה

הערה נשמרת פעמיים: `noteHtml` הוא ה-markup שמוצג, ו-`note` הוא מראה הטקסט שלו.
הטקסט הוא מה שמזין את החיפוש, את ייצוא ה-Markdown והטקסט, ואת הנפילה עבור
רשומות שנכתבו לפני שהיו הערות עשירות. שניהם נכתבים יחד בכל שמירה.

**הסינון מתבצע ביציאה, לא בכניסה.** `noteHtml` יכול להגיע מקובץ גיבוי שהתוסף
מעולם לא כתב, ולכן כל מסלול שהופך אותו חזרה ל-markup — כרטיס ברשימה, מילוי
העורך, ייצוא ל-HTML — מריץ `MarkerRichText.sanitize` מחדש. הסתמכות על "כבר
סיננו את זה כששמרנו" היא בדיוק ההנחה שקובץ גיבוי זדוני שובר.

השכבות מופרדות במכוון:

- **המדיניות** — אילו תגיות, אילו כתובות, אילו גדלי גופן — יושבת ב-
  `marker-domain.js` (`noteTagFor`, `safeNoteHref`, `safeNoteFontSize`). היא
  טהורה, ולכן `test/domain.test.js` בודק אותה מול רשימת התקפות: `<script>`,
  `<iframe>`, `javascript:`, `data:`, `java\tscript:`, `-moz-binding`, נתיב
  יחסי, ועוד.
- **ההפעלה** — הליכה על ה-DOM — יושבת ב-`marker-richtext.js`. הקלט נפרס
  ב-`DOMParser` (מסמך inert: סקריפטים אינם רצים, תמונות אינן נטענות), ולא
  ב-`innerHTML` של אלמנט חי.

בלי הפיצול הזה ה-sanitizer לא היה ניתן לבדיקה כלל: אין DOM ב-Node, והתוסף
מתחייב לאפס תלויות.

העורך עצמו נשען על `document.execCommand` להדגשה, נטוי, קו תחתי, קו חוצה,
כותרת, רשימות, ציטוט וקישור — כדי לקבל את התנהגות ה-undo המקורית של המנוע.
שני חריגים: `<mark>` מיושם ידנית דרך ה-Range API (ל-`hiliteColor` אין צורה
שה-allowlist יכול לסמוך עליה), וגודל הגופן נכתב כ-`font-size` מילולי אחרי
`styleWithCSS`. הדבקה עוברת דרך אותו sanitizer לפני שהיא נכנסת למסמך.

## i18n

עברית היא שפת המקור, וכל מחרוזת עברית משמשת גם כמפתח שלה. קטלוג הוא מפה שטוחה
מהמחרוזת העברית לתרגום.

- קוד: `t('הדגשות')`.
- HTML: `data-i18n` על האלמנט, או `data-i18n-attr="title,aria-label"` לתכונות.
  ה-HTML הסטטי נשאר עברית ו-`dir="rtl"` (ולידציית העיצוב דורשת זאת);
  `MarkerI18n.translateDocument` מתרגם בזמן ריצה ומחליף `lang`/`dir`.
- מקור השפה: בחירה מפורשת בהגדרות התוסף גוברת על שפת אוצריא. שינוי שפה בזמן
  ריצה מגיע ב-`settings.changed` עם המפתח `key-settings-language`.
- שמות הפריטים בתפריט ההקשר מתורגמים גם הם — `syncContributions` מעביר את `t`
  אל בוני ה-payload ב-`marker-domain.js`.

**כיסוי התרגום נאכף אוטומטית.** `test/i18n.test.js` סורק את כל קריאות `t()`
ואת כל סימוני ה-HTML, ונכשל אם מחרוזת חדשה חסרה בקטלוג האנגלי, אם נשאר בקטלוג
מפתח שכבר אינו בשימוש, אם תרגום איבד placeholder, או אם תרגום זהה למקור.
מחרוזת שמגיעה ל-`t()` דרך משתנה חייבת להירשם ב-`DYNAMIC_STRINGS` שב-
`test/helpers/i18n-strings.js`.

## גיבוי

- **אוטומטי**, במרחב הפרטי של התוסף (`fs.writeFile`, ללא הרשאה): `backups/latest.json`
  ועותק יומי, עם שמירת חמישה ימים אחרונים. מופעל בהשהיה של עשר שניות אחרי כל
  שינוי, כדי שעריכה מרוכזת לא תכתוב פעם לכל רשומה. רץ מכל מופע שביצע שינוי, לא
  רק מהמנוע — עריכות מהדף חייבות גיבוי בדיוק כמו סימון מהתפריט.
- **ידני**, לקובץ שהמשתמש בוחר: הבייטים עוברים ב-`fs.beginBinaryWrite` +
  `fs.commitUserFileWrite`, לא בגשר ה-JSON-RPC. זה גם המסלול היחיד שעובד בפועל
  ב-WebView של אוצריא — `window.open` מנוטרל שם והורדה דרך `<a download>` אינה
  אמינה.
- ייבוא שומר snapshot ומגלגל אחורה את ההדגשות וההגדרות אם משהו נכשל באמצע.
- `parseBackup` מקבל גם קבצי `schemaVersion: 1` מהגרסה הקודמת.

## דיווח למפתח

`feedback.report` שולח דיווח לאתר אוצריא, שמעביר אותו למפתח התוסף. הקריאה מנהלת
חסם זמן משלה וממתינה לדיאלוג האישור של אוצריא — **אין לעטוף אותה ב-timeout
מקומי**; ביטול מצד התוסף היה קוטע דיווח שהמשתמש באמצע אישורו. הקוד מוסיף
אוטומטית גרסת תוסף, גרסת אוצריא, פלטפורמה, שפה ומספר הדגשות. `feedback.hasReporterEmail`
נבדק מראש כדי לא לבקש כתובת שממילא תידרס.

## איפה לדבג

לוגים מתחילים ב-`[marker]` ונושאים את שם השכבה: `[marker][core]`,
`[marker][ui]`, `[marker][sdk]`, `[marker][events]`.

| התסמין | איפה לחפש |
|---------|-----------|
| הסימון לא נוצר | `[marker][core] Failed applying highlight`, ואחריו `MarkerSdkError.code` |
| ההדגשות נעלמות כשסוגרים את לשונית התוסף | אין מנוע רקע: `app.run_on_startup` כבויה, או `contributes.background.entrypoint` נפל מהמניפסט. בדקו את `runMode` ב-`plugin.boot` של המופע החי |
| ההדגשות נעלמות אחרי כשלוש דקות | `keepAlive` — `app.background_keep_alive` כבויה, או `startup.keepAlive` אינו `true` |
| לחיצה על צבע פותחת את לשונית התוסף | אותה הרשאה. זו נפילת ה-Host המתועדת, לא באג בתוסף |
| שינוי בדף אינו מגיע לספר | `pollRevision` — האם `bumpRevision` נקרא אחרי הכתיבה, והאם `REVISION_KEY` באמת השתנה באחסון |
| שני עותקים של אותו סימון בצבעים שונים | **לא** ריבוי מופעים — ה-Host עושה dedup לפי `(ownerPluginId, highlightId)`. חפשו שתי רשומות עם `highlightId` שונה על אותו קטע, או `reconcileHighlights` שטרם הדביק סגנון שהשתנה במקום אחר |
| התפריט לא מציג את הצבעים הנכונים | `syncContributions` ב-`marker-core.js`; בדקו אם `menuSignature` חסם עדכון |
| התפריט לא מופיע כלל | ההרשאה `app.startup_contributions` בהגדרות התוסף |
| לחיצה על צבע לא עושה כלום | אין תלות ב-`isEngine`. בדקו את ניתוב ה-Host (`pickContributionTarget`), את `whenBooted()`, ואת יומן ה-`[marker][sdk]` — קריאה שנדחתה ב-`error.rate_limited` הייתה הגורם ב-0.9.5 |
| הדגשה נעלמה אחרי הפעלה מחדש | `reconcileHighlights` — האם `status` הוא `failed_to_anchor` |
| טקסט נשאר עברית באנגלית | חסר `data-i18n` ב-HTML, או מחרוזת שמגיעה ל-`t()` דרך משתנה |
| עיצוב בהערה נעלם בשמירה | ה-`sanitize` הוריד אותו — בדקו את `noteTagFor` / `safeNoteFontSize` |
| קישור בהערה לא נשמר | `safeNoteHref` מקבל רק `http`/`https` מוחלטים |
| „ייצוא ל-PDF” מחזיר `error.forbidden` | הקריאה לא יצאה ישירות מ-handler של לחיצה |
| „הסימון נכשל: אוצריא דחתה את הנתונים” | payload שאינו בחוזה — ראו „חוזה ה-payload” למעלה; ההודעה מ-`error.invalid_params` מציינת את השדה |
| „ערוך הערה” לא פותח כלום | ההדגשה אינה במאגר הדף; בדקו את `pendingEditId` ואת סדר ה-boot |

`MarkerSdkError` נושא `method`, `code`, `category`, `retryable` ו-`isUnsupported`.
`isUnsupported` הוא ההבדל בין "המארח הזה לא מכיר את הקריאה" (מדלגים) לבין כשל
אמיתי (מדווחים).
